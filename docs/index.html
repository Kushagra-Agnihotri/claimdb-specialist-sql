Small-Judge Specialist-SQL for ClaimDB

Can a small open-source LLM judge verify database claims more accurately by delegating SQL generation to a specialist NL2SQL model? A systematic evaluation on the ClaimDB benchmark using BIRD dev databases.

Midsem complete Endsem in progress

Research Question

ClaimDB is a benchmark for claim verification over relational databases. A judge LLM receives a natural-language claim and must label it ENTAILED, CONTRADICTED, or NOT ENOUGH INFO by querying a SQLite database.

Small open-source judges (≤14B parameters) struggle with SQL generation — about 35–55% of their SQL calls return errors. We test whether delegating SQL writing to a dedicated NL2SQL specialist model improves accuracy without scaling the judge.

Error Analysis

Claims were grouped by query-error type to understand where the specialist helps. On ENTAILED and CONTRADICTED claims only (NOT ENOUGH INFO excluded):

Query outcome group n (A) Acc (A) n (C) Acc (C) Key finding
All queries ran successfully 86 75.6% 115 80.0% Specialist gets more claims into "clean" territory
Hit missing-table/column error 35 22.9% 12 50.0% Specialist drastically reduces grounding errors
Other query error 16 50.0% 7 42.9% Smaller group, similar accuracy
Never queried the database 3 33.3% 6 50.0% Rare; judge sometimes skips tool use

The specialist's advantage comes primarily from eliminating schema-grounding errors (missing table/column) — these drop from 25% of claims to 9%. When queries do run cleanly, both setups perform similarly (~75–80%), confirming that the judge's reasoning is adequate once it gets good data.

Infrastructure & Sweep Framework

run_judge.py

Core evaluation loop. pydantic_ai Agent with tool-calling against SQLite. Supports conditions A/B/C/CS.

builder.py

NL2SQL specialist wrapper. Supports Arctic, OmniSQL, FINER-SQL prompt templates via OpenAI-compatible API or HuggingFace.

providers.py

Provider abstraction for Ollama (local GPU), Groq (free cloud), OpenRouter. Live model catalog validation.

sweep_lib.py

Error-aware retry engine. Classifies failures (dead model, rate limit, too large, transient) with adaptive backoff.

sweep_judges.py

Multi-model judge sweep: 6+ open-source models × conditions A/C. Resumable JSONL output.

score.py

Scoring with bootstrap CIs, macro-F1, per-class recall, exact McNemar test for pairwise comparison.

Compute

  • Midsem runs: NVIDIA RTX 4070 Super (personal GPU), ~30–60 min per 210-claim condition
  • Endsem runs: BITS Pilani Sharanga HPC — A100, H100, H200, V100 partitions via SLURM
  • Cloud fallback: Groq / OpenRouter free-tier APIs for rapid iteration

Endsem Experiment Roadmap

In progress 6+ Open-Source Model Comparison (Condition A)

Evaluate 2–3 Qwen (qwen3:4b, qwen3:8b, qwen3:14b), 2 Mistral (mistral:7b, mistral-nemo:12b), and 2 LLaMA (llama3.2:3b, llama3.1:8b) judges under Condition A to establish model-specific baselines across the small-model spectrum.

Planned NL2SQL Builder Variations

Test Arctic-Text2SQL-R1-7B as the builder with different judges: Qwen3-8B (done), Llama3.1-8B, and other models from the comparison above. Also evaluate alternative builders: OmniSQL, FINER-SQL/SLM-SQL.

Planned Arctic Self-Delegation Baseline

Use Arctic-Text2SQL-R1-7B as both judge and builder — a self-delegation control to determine if the specialist advantage comes from task separation or the specialist model itself.

Planned Tool-Call Tracking

Instrument the number of tool calls per claim as an efficiency metric. Hypothesis: the specialist reduces wasted calls (retries on bad SQL) so the judge converges faster.

Planned TableFact Dataset

Extend evaluation to the TableFact dataset (Chen et al., 2020) as a secondary benchmark with flat tables, testing generalization beyond BIRD's relational schemas.
